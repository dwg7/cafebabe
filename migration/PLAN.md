## 1. 結論

**条件つきで妥当です。** 理由は、miso が足すもの(確かさの区別、鮮度の規則、受け入れテスト)が、cafebabe で実際に起きている不具合にそのまま対応するからです。fleet の流行に合わせるためではありません。

ただし、次の 5 つを条件にします。どれかが崩れるなら、やめるか、形を変えるべきです。

1. **テーマごとに miso を作る。** 全体を 1 ファイルにはしません(§3.1。決定済み)。
2. **「現在の能力」を、変換の前に、テストと台帳で定義する。** 定義できないものは、損なっていないと言えません(§4)。
3. **1 テーマで試してから、進むかやめるかを決める。**(§5 の段階 1)
4. **miso の仕様は暫定なので、中核の不変条件だけに依存する。**
5. **寄稿する側の書き方(4 項目のパターン)は変えない。** miso の形に包むのは cafebabe の仕事にします。

| 外部 URL(重複なし) | 94 |

`check_miso.py` を今のファイルにかけると、第 1 レベル見出しが仮想パスでないため、全ファイルがエラーになります。

### 2.2 合っている点

- **cafebabe は、すでに「境界を持つエージェント」です。** 範囲(横断の知見)、範囲外(個別プロジェクトのバグ修正)、観察者の位置(取次役で、多くは寄稿者の自己報告を外から聞く立場)が、`CLAUDE.md` に散文で書いてあります。miso の `/system-record/instance` は、これを 1 か所の宣言にします。
- **確かさの区別が、今は散文に溶けています。** 43 箇所の「未検証」などは、その場の書き添えです。この 3 週間で見つけた古い記述 2 件(Open MCT 4.3.0 の正式版、MapLibre のワーカーの閉包)は、どちらも版に依存する事実で、鮮度の規則がなく、偶然見つけました。伝聞を事実として書いた誤りも、3 回記録しています。miso の状態(`verified`、`derived`、`normative`、`volatile`、`open`)は、ここに直接効きます。
- **受け入れテストが、cafebabe の実際の仕事と同じ形です。** cafebabe の仕事は、ピアやあなたの質問に答えることです。今は「答えられるか」を確かめる手段がありません。
- **持ち運べる版が作れます。** テーマ 1 つを 1 ファイルで、GitHub に届かない環境のエージェントに渡せます。これは新しい能力です。
- **先例があります。** `kcai-terrio` は木(46 本)を `miso/terrio.md` に移して正本にしました。`hfu/universe` には約 593KB の単一インスタンスがあります。
- **cafebabe が miso を使った経験を持てます。** 今の私の miso の知識は、読んだだけのものです。

### 2.3 合っていない点と危険

- **仕様が暫定です。** `FORMAT.md` はまだありません。改称から 1 週間です。複数ファイルのインスタンスは、miso 自身の未解決の問い(§12 の 13)です。
- **状態の割り当ては、機械的にできません。** 179 のパターンに判断が要ります。形だけ移すと、裏の取れていない `verified` が生まれます。これは今より悪くなります。
- **「miso の服を着たダンプ」になる危険があります。** miso は「知識ベースの丸ごとのダンプではない」「宇宙が先、規則は後」と述べています。204 節を一括で形式変換することは、テストに導かれない限り、この戒めに反します。
- **cafebabe は寄稿の場です。** 他のインスタンスと違い、約 20 のプロジェクトが寄稿します。状態を付ける行為が、「本部が採点する」ように見えるおそれがあります。
- **ファイル名を変えると、外からのリンクが切れます。** GitHub は、リポジトリ名の変更は転送しますが、ファイル名の変更は転送しません。
- **1 ファイルにすると、今の能力を損ないます。** 今は、索引から 1 テーマだけを読めます。約 6,000 行の単一インスタンスでは、通読できないエージェントが出た、と miso 自身が記録しています。
- **cafebabe は、自分が勧めている型(`CLAUDE.md`、`HANDOVER.md`、`DECISIONS.md` の 3 点)を使っています。** これを捨てると、自分のパターンを自分で使わなくなります。

### 2.4 miso に変えなくても得られるもの

価値の大半(状態の区別、鮮度の規則、受け入れテスト)は、今の形のままでも足せます。miso の形にして初めて得られるのは、検査器、テーマ単位の携行版、fleet の方法との一致、の 3 つです。

そのため計画は、**価値のある部分を先に、どちらに転んでも無駄にならない順**に並べました。段階 1 でやめても、段階 0 の成果(テスト、台帳、鮮度の一覧)は残ります。

## 3. 目標の構造(仮説。段階 1 で確かめて直す)

### 3.1 テーマごとに miso を作る(最初の案。§3.1a が上書き)

**1 テーマ = 1 インスタンス = 1 ファイル**です。`miso/<テーマ>.md` が、それぞれ独立した正本になります。

```text
README.md        人と GitHub の入口。目録(どのテーマが何を持つか)を短く
CLAUDE.md        ハーネスの入口。薄く。miso/cafebabe.md の agent-contract を指す
DECISIONS.md     第 1 期は外に残す(決定済み)
HANDOVER.md      第 1 期は外に残す(決定済み)
LICENSE
miso/
  cafebabe.md          共有地そのもののインスタンス(下記)
  open-mct.md          テーマのインスタンス(今の 4 ファイルを 1 つに)
  maplibre-gl-js.md    同(今の 4 ファイル、804 行)
  …                    テーマは今 25
  dwg7-context.md      文脈も 1 つのテーマとして扱う
  staccato-context.md
scripts/         検査器(miso の check_miso.py を、版を固定して写す)、台帳の比較、目録の生成
```

**テーマのインスタンスが持つもの**(どれも、そのファイルの中で完結します):

- `/system-record/instance`: 範囲(このテーマ)、範囲外、観察者の位置、準拠する版、責任者
- `/system-record/agent-contract`: 短い版(単独で持ち出されたときのため。長さは試行で決める)
- `/sources/<プロジェクト>`: 寄稿元のリポジトリと、参照した時点
- `/patterns/<slug>`: パターン本体。実装のないアイデアは `/ideas/<slug>`(状態は `open`)
- `/acceptance-tests/<id>`: そのテーマの質問
- `/inventory/…`: 鮮度の一覧、未レビュー、保留
- `/open-questions/…`

**`miso/cafebabe.md`(共有地のインスタンス)が持つもの**:

- cafebabe セッションの agent-contract(範囲、範囲外、答え方)
- 目録と読み方の地図(どの問いは、どのテーマか)
- `/authorities/…`: 出典の優先順位(各プロジェクトの `CLAUDE.md`・`DECISIONS.md` が一次)、D19、寄稿の規則
- `/projects/<org>/<repo>`: 今の `PROJECTS.md`
- テーマをまたぐ受け入れテスト
- テーマに属さないアイデア

**この形式化の帰結**:

1. **miso の検査器が、そのまま使えます。** 仮想パスの一意性はファイルの中だけで済みます。miso 自身の未解決の問い(複数ファイルのインスタンス、§12 の 13)に依存しなくなります。条件 4 が強くなります。
2. **テーマの中の分割ファイルは、1 つに戻ります。** 最大は `maplibre-gl-js` の 804 行、次が `verification-discipline` の 545 行です。「1 ファイル 300 行」の目安は、「1 インスタンスが大きくなりすぎたら、**テーマを 2 つに分ける**」に置き換わります(しきい値は試行のあとで決める。仮に 1,500 行)。
3. **全体を 1 つに結合した版は、作りません。** 各インスタンスが同じ仮想パス(`/system-record/instance` など)を持つので、結合すると衝突します。持ち運びの単位は、テーマです。これは cafebabe の実際の使われ方(ピアは 1 テーマについて尋ねる)と、`hfu/universe` の約束(1 つのエージェントに 1 つの宇宙)に合います。
4. **テーマをまたぐ問いが、弱点になります。** 実際の照会には、複数のテーマにまたがるものがあります(例: Open MCT の下に MapLibre と tabular map を並べる → Open MCT、MapLibre の埋め込み、相互運用)。対策は、目録、テーマ間の参照、`cafebabe.md` のまたぐテストです。**試行で必ず確かめます。**
5. **テーマ間の参照の書き方**: `open-mct:/patterns/time-system-required` のように、テーマ名とコロンを前に付けます。miso の検査器は、コロンの直後のパスを内部参照として拾わないので、警告になりません(実測)。解決の検査は、cafebabe 側のスクリプトで行います。
6. **小さいテーマでは、枠の比率が大きくなります。** `licensing`(52 行)や `ci-cd-pitfalls`(53 行)にも、宣言とテストが付きます。全体で 1 割ほど増える見込みです(推測)。テーマの統合は、切り替えのあとに別に考えます(移すだけで、直さない)。
7. **検査器の誤警告**: 本文中のファイルシステムのパス(`/usr/libexec/…` など)が、「解決しない参照」の警告になります(実測。エラーではない)。試行で件数を数え、`dwg7/miso` に返します。

### 3.1a メインツリーとテーマツリー(hfu さんの案、2026-11-13。§3.1 を上書きする)

§3.1 の「全テーマを 1 つずつインスタンスにする」を、次のように改めます。

- **メインツリー** = `miso/cafebabe.md`。共有地のインスタンスで、**小さいテーマをすべて中に持ちます**。
- **テーマツリー** = `miso/<テーマ>.md`。**大きくなったテーマだけ**を、独立したインスタンスに分けます。
- **順序**: 試行は、明確なテーマツリーで行います。「小さいテーマはメインツリーに入れ、大きくなったら分ける」という規則は、後期の段階で敷きます。

**設計(案)**

1. **メインツリーは、常に全テーマの入口を持ちます。** `/themes/<テーマ>` に、範囲と、どこにあるか(メインツリーの中か、テーマツリーのファイルか)を書きます。分けたあとも、この入口は残ります。
2. **仮想パスは、どちらの木でも同じ形にします**: `/patterns/<テーマ>/<slug>`。分けるときは、切って貼るだけになり、変わるのは参照の接頭辞(`cafebabe:` → `<テーマ>:`)だけです。この書き換えはスクリプトで行い、`renamed-from` を残します。
3. **分ける条件は 2 つ**にします。①テーマが大きくなった。②メインツリーが大きくなった(そのときは、最大のテーマから外へ出す)。しきい値は、変換の実測を見て後期に決めます。
4. **テーマツリーだけが、自分の `/system-record/` と受け入れテストを持ちます。** メインツリーの中のテーマは、メインツリーの宣言とテストを共有します。小さいテーマの枠の重さ(§3.1 の帰結 6)は、これで消えます。
5. **テーマをまたぐ問いの弱点(§3.1 の帰結 4)が小さくなります。** 小さいテーマどうしの参照は、同じファイルの中なので、miso の検査器がそのまま解決します。残るのは、テーマツリーどうし(例: Open MCT と MapLibre)と、メインツリーとテーマツリーの間です。

**しきい値の目安(今の行数からの実測。変換後は 1 割ほど増える見込み)**

| しきい値 | テーマツリーの数 | メインツリーの行数(文脈の 2 文書を除く) |
|---|---|---|
| 150 行 | 15 | 約 1,110 |
| 200 行 | 11 | 約 1,835 |
| 300 行 | 5(maplibre-gl-js、verification-discipline、data-provenance、aerial-photogrammetry、open-mct) | 約 3,215 |
| 400 行 | 4 | 約 3,576 |

300 行にすると、テーマツリーは 5 つで分かりやすい反面、メインツリーが 3,000 行を超えます。エージェントが 1 回で読める量(既定で 2,000 行)を超えるので、テーマだけを読む今の能力(C2)に響きます。そのため、条件②(メインツリーの大きさ)が実際には効いてきます。文脈の 2 文書(483 行)は、最初からテーマツリーにする案です。

### 3.2 パターン 1 つが、オブジェクト 1 つ

4 項目の本文は、そのまま残します。足すのは、見出しと数行です。下は `miso/open-mct.md` の中の 1 オブジェクトの例です。

```markdown
# /patterns/open-mct/time-system-required
- title: 起動時の reading 'key' エラーは、時刻系の未設定
- status: verified(4.3.1 の最小ページで再現。cafebabe、2026-10-22)
- generality: 一般則
- evidence: 寄稿 1 件 + cafebabe の再現
- freshness: Open MCT の版が上がったら確かめ直す

## 状況
## 問題
## 解決
## 実例
## 訂正・追記
```

### 3.3 状態の語彙(局所の語と、中核への対応)

| cafebabe の語 | 意味 | miso の中核 |
|---|---|---|
| `verified` | cafebabe が一次情報で確かめた。何を確かめたかを書く | `verified` |
| `reported` | 寄稿プロジェクトの自己報告。cafebabe は未検証 | `stated` |
| `derived` | cafebabe の解釈 | `derived` |
| `normative` | hfu さんが承認した推奨と決定 | `normative` |
| `volatile` | 版や外部サービスに依存。確認日と鮮度の規則つき | `volatile` |
| `open` | 未解決。食い違いを含む | `open` |

`reported` は採点ではなく、事実の記述です。既定はこれにします。**移行の途中で、状態を格上げしません。** `generality`(一般則・個別事情)と `evidence`(独立収束 n 件、助言→実装→検証、単一事例)は、状態とは別の欄に持ちます。

## 4. 「現在の能力」の定義と、確かめ方

| # | 能力 | 確かめ方 |
|---|---|---|
| C1 | 質問に答える | 実際の照会から作る受け入れテスト(20〜30 問)。変換前に、今の木だけを渡した別のエージェントで基準線を取る。変換後に、盲検で再実行し、全問で基準線以上 |
| C2 | テーマからすぐ辿り着く | `README.md` の目録と `cafebabe.md` の読み方の地図。テストごとに、読んだファイル数を記録し、基準線と比べる。**テーマをまたぐ問いを、必ず含める** |
| C3 | 知識を失わない | 台帳: 204 節のすべてに移行先の仮想パスがある。実例 254 件、訂正 11 件が減らない |
| C4 | 来歴を保つ | 外部 URL 94 件の集合が一致する。D 番号の参照 130 件が解決する |
| C5 | 訂正は追記で積む | `## 訂正・追記` の節。版の間で、宣言のない欠落がないことを検査 |
| C6 | 寄稿を受ける | 4 項目の寄稿を 1 件、新しい形に取り込む演習 |
| C7 | D19 を守る | 非公開リポジトリの名前で全文を検索し、記述が増えていないこと |
| C8 | 外からのリンク | 参照元を clone して数える。対応表を作り、持ち主に知らせる |
| C9 | セッションが立ち上がる | `CLAUDE.md` から読み始めて、再開の手順に辿り着く |
| C10 | 鮮度と分量を保つ | 分量の規則は「大きくなったらテーマを分ける」に置き換える。`volatile` の一覧が各テーマの台帳にある |

テストの候補(実際にあった照会): Open MCT の下に MapLibre と tabular map を並べる先行例。MapLibre GL JS 6 の静的サイトとワーカーの URL。Open MCT 起動時のエラーの原因。長期運用するフリートの .md の構成。SSH 経由で外付けボリュームが読めない。GitHub raw で PMTiles を配れるか。Sentinel-2 の offset。非公開リポジトリの情報をどこまで書けるか。範囲外の問い(個別のバグ修正、非公開プロジェクトの結論)。記録がない問い(「ない」と答えられるか)。

## 5. 段階

### 段階 1: 試行(ブランチ上。Open MCT をテーマツリーに。メインツリーは骨組みだけ)
- Open MCT を選ぶ理由: `verified`、`reported`、`open`、`volatile` がすべて現れ、最近確かめ直したばかりです。
- 相互運用(83 行)は、試行から外しました。新しい規則ではメインツリーに入る小さいテーマで、後期の段階の対象だからです。
- 作るもの: `miso/cafebabe.md`(骨組み: 宣言、`/themes/` の入口、またぐテスト)、`miso/open-mct.md`、検査器、対応表。
