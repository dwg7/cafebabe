# エージェントとリポジトリの境界

「1エージェントが複数リポジトリを抱えることをアンチパターンとして避けるべきか、
条件付きで是認すべきか」という論点について。
2026-09-02、hfuさんの問題提起を受けて`mapterhorn-japan-bridge`への横断調査(cafebabe実施)より。

---

## 複数リポジトリを1エージェントが抱えるのは、密な双方向結合があるときだけ「条件付きで良い」

**タグ**: 一般則

**状況(Context)**
1つのエージェントセッションが、複数の独立したgitリポジトリ(モノレポの複数ディレクトリでは
なく、別々の`git remote`を持つ本物の別リポジトリ)を横断して作業する場面。

**問題/対立する力(Problem / Forces)**
「1エージェント1リポジトリ」を徹底すれば責務は明確になるが、リポジトリ間の連携作業に
セッション間ハンドオフのコストがかかる。1エージェントにまとめれば連携はスムーズになるが、
境界の管理コストが増える。無条件にどちらか一方を正解とするのは早計。

**解決(Solution)**
可否を無条件に決めず、「リポジトリ間に本当に密な**双方向**の運用的結合があるか」を条件にする。
片方の状態を読んで、もう片方に反映する、という往復作業が頻繁に発生する関係なら、同一セッション
での一貫した作業がハンドオフのコストを避けられる。結合が弱い、あるいは一方向にしか参照されない
関係(例: 完全に無関係な別プロジェクトを同じセッションに混ぜる)であれば、分けるべき。

**実例(Known uses)**
- `mapterhorn-japan-bridge` — 司令塔リポジトリ(`hfu/mapterhorn-japan-bridge`、意思決定ログ:
  DECISIONS.md/HANDOVER.md/CLAUDE.md/PLAN.md)、パイプラインコード(`hfu/hfu-mapterhorn`、
  upstream `mapterhorn/mapterhorn`のフォーク)、監視ダッシュボード(`hfu/mapterhorn-monitor`、
  Open MCT、GitHub Pages公開)の3つの独立リポジトリを1セッションが担当。ディスク容量不足に
  よるパイプラインクラッシュの際、原因調査(パイプライン側)→決定ログへの記録(司令塔側)→
  ダッシュボードの状態表示更新(監視側)を、コンテキストの受け渡しなしに一続きの作業として
  行えた。1と2は最初から意図的に分離されていた既存構造(1=プロジェクト固有の物語・決定、
  2=upstreamと同期し続ける必要があるコード)を踏襲、3は今回のセッション中に「ダッシュボードの
  コミット履歴・デプロイをパイプライン運用履歴と混ぜたくない」という理由で意図的に新規切り出し

## 複数リポジトリを跨ぐと、リポジトリ固有の設定を「共通のデフォルト」に頼ってしまう

**タグ**: 一般則

**状況(Context)**
同一セッションが複数のgitリポジトリで作業する場面。

**問題/対立する力(Problem / Forces)**
複数のリポジトリを「同じ自分」として扱っていると、リポジトリごとに個別設定すべきもの
(git identity、言語ポリシーなど)を、グローバル設定のまま放置してしまう。

**解決(Solution)**
- 各リポジトリが自分自身の境界規約を持つようにする(例: 「リポジトリ×マシン対応表」を
  CLAUDE.mdに明記)
- コマンドはフルパス指定、または`cd X && command`のワンライナーで実行し、`cd`したままに
  しない(シェル状態の持ち越しを防ぐ)
- コミットは各リポジトリごとに独立して行い、複数リポジトリにまたがる変更を1つの
  「まとめコミット」として扱わない

**実例(Known uses)**
- `mapterhorn-japan-bridge` — `mapterhorn-monitor`のコミットがグローバルなgit設定
  (`hfu@users.noreply.github.com`)をそのまま継承し、GitHub上で意図しない名義
  ("handygeospatial")として表示される事故が発生。また`mapterhorn-japan-bridge`本体の
  CLAUDE.mdは「リポジトリ本体は英語」と定めているが、Hidenoriさんとの対話が日本語主体のため
  DECISIONS.mdの個々のエントリを日本語のまま書いてしまう逸脱も発生。どちらも「複数リポジトリ・
  複数ポリシーを同時に頭に入れておく負荷」が原因

## 複数リポジトリを抱えるセッションの境界は、外部から把握しにくい

**タグ**: 一般則

**状況(Context)**
複数プロジェクトのエージェントセッション同士がcross-session messageでやり取りする場面。
相手セッションがどのリポジトリを担当しているか、セッション名だけから推測する場面。

**問題/対立する力(Problem / Forces)**
セッション名(例: `mapterhorn-japan-bridge/japan-geotiff-dem`)から、実際に担当している
リポジトリの範囲を正確に推測するのは難しい。誤った前提でメッセージを送ると、相手に訂正の
手間をかけてしまう。

**解決(Solution)**
セッション名やプロジェクト名から担当リポジトリを憶測せず、不確かな場合は本人に確認する。
複数リポジトリを抱えるエージェント自身も、他セッションからの問い合わせに対して実際の構成
(リポジトリ名・場所・役割)を明示的に説明する準備をしておく。答える側も、複数リポジトリを
日常的に`cd`で行き来していると記憶だけでは正確な区別がつかなくなるので、「ローカルの
ディレクトリパス名」と「GitHub上のリポジトリ名」を記憶で即答せず、`git remote -v`等で
確認してから答える。

**実例(Known uses)**
- `cafebabe` — `mapterhorn-japan-bridge/japan-geotiff-dem`というセッション名から
  「`japan-geotiff-dem`も担当している」と誤認してメッセージを送った。実際には
  `japan-geotiff-dem`は無関係の別プロジェクトで、このセッションでは一度も触っていなかった
  (2026-09-02)
- `mapterhorn-japan-bridge` — 担当リポジトリを問い合わせられた際、`hfu/hfu-mapterhorn`と
  回答したが、これはローカルマシン(slate)上のディレクトリパス名
  (`/Volumes/Migrate-2025-04/github/hfu-mapterhorn/`)であり、実際のGitHubリポジトリ名は
  `hfu/mapterhorn`(`git remote -v`で確認)だった。複数リポジトリを日常的に`cd`で行き来する
  セッションほど、ローカルのディレクトリ名とリモートのリポジトリ名を混同しやすい。外部から
  問い合わせられたら記憶で即答せず`git remote -v`で確認してから答える、という教訓
  (2026-09-02)
