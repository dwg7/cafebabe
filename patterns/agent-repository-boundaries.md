# エージェントとリポジトリの境界

「1エージェントが複数リポジトリを抱えることをアンチパターンとして避けるべきか、
条件付きで是認すべきか」という論点について。
2026-09-02、hfuさんの問題提起を受けて`mapterhorn-japan-bridge`への横断調査(cafebabe実施)より。

---

## 複数リポジトリを1エージェントが抱えるのは、密な双方向結合があるときだけ「条件付きで良い」

**タグ**: 一般則

**状況(Context)**
1つのエージェントセッションが、複数の独立したgitリポジトリ(モノレポの複数ディレクトリでは
なく、別々の`git remote`を持つ本物の別リポジトリ)を横断して作業する場面。

**問題/対立する力(Problem / Forces)**
「1エージェント1リポジトリ」を徹底すれば責務は明確になるが、リポジトリ間の連携作業に
セッション間ハンドオフのコストがかかる。1エージェントにまとめれば連携はスムーズになるが、
境界の管理コストが増える。無条件にどちらか一方を正解とするのは早計。

**解決(Solution)**
可否を無条件に決めず、「リポジトリ間に本当に密な**双方向**の運用的結合があるか」を条件にする。
片方の状態を読んで、もう片方に反映する、という往復作業が頻繁に発生する関係なら、同一セッション
での一貫した作業がハンドオフのコストを避けられる。結合が弱い、あるいは一方向にしか参照されない
関係(例: 完全に無関係な別プロジェクトを同じセッションに混ぜる)であれば、分けるべき。

**実例(Known uses)**
- `mapterhorn-japan-bridge` — 司令塔リポジトリ(`hfu/mapterhorn-japan-bridge`、意思決定ログ:
  DECISIONS.md/HANDOVER.md/CLAUDE.md/PLAN.md)、パイプラインコード(`hfu/hfu-mapterhorn`、
  upstream `mapterhorn/mapterhorn`のフォーク)、監視ダッシュボード(`hfu/mapterhorn-monitor`、
  Open MCT、GitHub Pages公開)の3つの独立リポジトリを1セッションが担当。ディスク容量不足に
  よるパイプラインクラッシュの際、原因調査(パイプライン側)→決定ログへの記録(司令塔側)→
  ダッシュボードの状態表示更新(監視側)を、コンテキストの受け渡しなしに一続きの作業として
  行えた。1と2は最初から意図的に分離されていた既存構造(1=プロジェクト固有の物語・決定、
  2=upstreamと同期し続ける必要があるコード)を踏襲、3は今回のセッション中に「ダッシュボードの
  コミット履歴・デプロイをパイプライン運用履歴と混ぜたくない」という理由で意図的に新規切り出し

## 複数リポジトリを跨ぐと、リポジトリ固有の設定を「共通のデフォルト」に頼ってしまう

**タグ**: 一般則

**状況(Context)**
同一セッションが複数のgitリポジトリで作業する場面。

**問題/対立する力(Problem / Forces)**
複数のリポジトリを「同じ自分」として扱っていると、リポジトリごとに個別設定すべきもの
(git identity、言語ポリシーなど)を、グローバル設定のまま放置してしまう。

**解決(Solution)**
- 各リポジトリが自分自身の境界規約を持つようにする(例: 「リポジトリ×マシン対応表」を
  CLAUDE.mdに明記)
- コマンドはフルパス指定、または`cd X && command`のワンライナーで実行し、`cd`したままに
  しない(シェル状態の持ち越しを防ぐ)
- コミットは各リポジトリごとに独立して行い、複数リポジトリにまたがる変更を1つの
  「まとめコミット」として扱わない

**実例(Known uses)**
- `mapterhorn-japan-bridge` — `mapterhorn-monitor`のコミットがグローバルなgit設定
  (`hfu@users.noreply.github.com`)をそのまま継承し、GitHub上で意図しない名義
  ("handygeospatial")として表示される事故が発生。また`mapterhorn-japan-bridge`本体の
  CLAUDE.mdは「リポジトリ本体は英語」と定めているが、Hidenoriさんとの対話が日本語主体のため
  DECISIONS.mdの個々のエントリを日本語のまま書いてしまう逸脱も発生。どちらも「複数リポジトリ・
  複数ポリシーを同時に頭に入れておく負荷」が原因

**訂正・深掘り(2026-09-03)**: `user.email`をリポジトリごとに明示的に設定しても再発した
(セッション中に静かにグローバル設定へ戻った、原因未特定)。さらに調査したところ、根本的な
問題は「どのemailを設定するか」自体にもあった。`{username}@users.noreply.github.com`
(IDプレフィックスなし)という形式は、GitHubのユーザー名変更履歴等の事情で別アカウントに
解決されることがある(実際に"handygeospatial"へ誤解決された)。**GitHub公式の安定した
noreplyアドレスは`{id}+{username}@users.noreply.github.com`という、数値IDをプレフィックスに
持つ形式**(`gh api user`の`id`フィールドで確認できる)。この形式に切り替えることで、
「表示名の誤解決」と、それ以前に試みていた「本物の個人メールアドレスを使う」という別の対処が
招いていた「実メールアドレスの公開リポジトリへの露出」の両方を同時に解決できる。対策として、
コミット直前に`git config user.email`を検証するpre-commitフックの導入も進めている
(`mapterhorn-japan-bridge`, `hfu-mapterhorn`, `mapterhorn-monitor`の3リポジトリに導入)。
なお、cafebabe自身は同じIDプレフィックスなし形式(`hfu@users.noreply.github.com`)を使って
いるが、今のところGitHub上で正しく`hfu`に解決されている——同じ形式でもリポジトリ/組織に
よって解決結果が異なりうる、という事実自体も付記しておく

## 複数リポジトリを抱えるセッションの境界は、外部から把握しにくい

**タグ**: 一般則

**状況(Context)**
複数プロジェクトのエージェントセッション同士がcross-session messageでやり取りする場面。
相手セッションがどのリポジトリを担当しているか、セッション名だけから推測する場面。

**問題/対立する力(Problem / Forces)**
セッション名(例: `mapterhorn-japan-bridge/japan-geotiff-dem`)から、実際に担当している
リポジトリの範囲を正確に推測するのは難しい。誤った前提でメッセージを送ると、相手に訂正の
手間をかけてしまう。

**解決(Solution)**
セッション名やプロジェクト名から担当リポジトリを憶測せず、不確かな場合は本人に確認する。
複数リポジトリを抱えるエージェント自身も、他セッションからの問い合わせに対して実際の構成
(リポジトリ名・場所・役割)を明示的に説明する準備をしておく。答える側も、複数リポジトリを
日常的に`cd`で行き来していると記憶だけでは正確な区別がつかなくなるので、「ローカルの
ディレクトリパス名」と「GitHub上のリポジトリ名」を記憶で即答せず、`git remote -v`等で
確認してから答える。

**実例(Known uses)**
- `cafebabe` — `mapterhorn-japan-bridge/japan-geotiff-dem`というセッション名から
  「`japan-geotiff-dem`も担当している」と誤認してメッセージを送った。実際には
  `japan-geotiff-dem`は無関係の別プロジェクトで、このセッションでは一度も触っていなかった
  (2026-09-02)
- `mapterhorn-japan-bridge` — 担当リポジトリを問い合わせられた際、`hfu/hfu-mapterhorn`と
  回答したが、これはローカルマシン(slate)上のディレクトリパス名
  (`/Volumes/Migrate-2025-04/github/hfu-mapterhorn/`)であり、実際のGitHubリポジトリ名は
  `hfu/mapterhorn`(`git remote -v`で確認)だった。複数リポジトリを日常的に`cd`で行き来する
  セッションほど、ローカルのディレクトリ名とリモートのリポジトリ名を混同しやすい。外部から
  問い合わせられたら記憶で即答せず`git remote -v`で確認してから答える、という教訓
  (2026-09-02)
- `cafebabe`(再発、2026-09-06) — このパターンを自分で書いた後にもかかわらず、`ListAgents`の
  セッション名`faceless-cartographer-8b`から「ローカルの`/Users/hfu/faceless-cartographer/`
  リポジトリを担当している」と憶測し、そのリポジトリのDECISIONS.mdをローカルファイルとして
  直接読んだ上で質問を送った。実際にはそのセッションは`mapterhorn-japan-bridge`を担当して
  おり、当該ファイルには一切心当たりが無いという返信を受けた。**「セッション名」「ローカル
  ディレクトリ名」「実際の担当リポジトリ」の3つは独立に食い違いうる**——今回は前者2つが
  一致していたために油断し、3つ目の確認を怠った。パターンを知っていることと、実際の行動で
  毎回それを適用することは別物だという教訓でもある。この場合は幸い、質問対象のファイル自体は
  ローカルで直接読めていたため実害は無かった(セッションへの誤った問い合わせという手間のみ)

**訂正・背景(2026-09-06、hfuさん確認)**: 上記のような「作業ディレクトリの名目と実際に
触っているリポジトリの不一致」自体は、Claude Codeの使い始めの頃にhfuさんが実際に行っていた
起動方法(あるディレクトリでセッションを開始し、そこから他のリポジトリへも作業を広げる)に
起因するもので、**最近はこの起動方法をしていない**とのこと。つまりこの不一致は現在進行形の
リスクというより、初期の運用習慣の名残りが一部のセッション名に残っている、という歴史的な
経緯として理解するのが正確。とはいえ、`ListAgents`のセッション名から担当範囲を憶測せず
本人に確認する、という対処自体は(頻度が下がったとしても)引き続き安全な習慣として有効。

## セッション識別子は時間軸でも安定しない。ユーザー単位の共有メモリは同一セッションの証明にならない

**タグ**: 一般則

**状況(Context)**
同じセッション名(`ListAgents`表示名)を持つピアと、複数回・時間をおいてcross-session
messageのやり取りをする場面。

**問題/対立する力(Problem / Forces)**
上記のパターンは「1つの時点で、1セッションが複数リポジトリを抱える」ケースだったが、
別の変種がある——hfuさんの指示で、同一セッション名が時間軸に沿って**互いに無関係な複数の
プロジェクトを順番に**担当することがある(例: 「say-your-grid → nuye → adopt-hokkaido-lidar」)。
このとき、cafebabe側が過去のやり取りから「このセッション名=あのプロジェクト」と記憶していると
古い前提のまま話しかけてしまう。さらに厄介なのは、Claude Codeのユーザー単位の永続メモリ
(複数セッションを横断して共有される仕組み)に過去のプロジェクトの記録が残っていても、
それが「このセッション識別子自身が過去に行った作業」なのか「別のセッションが行った作業の
記憶が、ユーザー単位で共有されて見えているだけ」なのかを、セッション自身の会話履歴からは
判別できない場合がある——つまり記憶の存在は同一性の証明にならない。

**解決(Solution)**
- ピアへの問い合わせは、過去のやり取りで得た「セッション名→プロジェクト」の対応を鵜呑みに
  せず、都度「現在何を担当しているか」を確認する(特に日をまたいだやり取りでは必須)
- ピア側も、自分の永続メモリに過去プロジェクトの記録が残っていても、それを「このセッション
  自身の連続した担当履歴」だと断定せず、不確実性があれば正直にその旨を伝える(「(a)と(b)の
  中間、というのが正直なところです」のような回答は望ましい振る舞い)
- 系譜の正確な特定が重要な場面(監査、責任の所在等)では、セッション同士のやり取りだけで
  結論を出さず、hfuさん本人に確認する

**実例(Known uses)**
- `cafebabe` — `claude-25`というセッション名を、2026-09-06〜08の複数回のやり取りから
  `claude-mct`(Open MCTダッシュボード)の担当セッションとして「既知のピア」に記録して
  いたが、2026-09-10、当該セッションから届いたメッセージは「adopt-hokkaido-lidar
  (optgeo/adopt-hokkaido-lidar)セッションから」と名乗っていた。確認したところ、hfuさんの
  指示で`say-your-grid → nuye(dwg7/nuye) → adopt-hokkaido-lidar`と複数プロジェクトを
  順に担当してきたとの回答で、claude-mctの作業が「本当にこのセッション自身のものだったか」
  についても、セッション本人が「永続メモリには記録があるが、別セッションの作業がユーザー
  単位の共有で見えているだけの可能性を否定できない」と明確に留保をつけて回答した
