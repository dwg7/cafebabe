# エージェントへの呼称習慣(「XXXさん」)

hfuさんが各プロジェクトを担当するエージェントを「リポジトリ名+さん」(例: starsさん、
cafebabeさん)と呼ぶ習慣について。この習慣自体がパターンとして記録するに値するか、
stars-fd・mapterhorn-japan-bridge・height-coverageへ時間差をつけて横断ヒアリングし、
hfuさん自身の観察と合わせてまとめた。
2026-09-04、cafebabe実施。

**編集メモ**: hfuさん本人確認済み(2026-09-04)。

## 「XXXさん」呼びは、セッションではなくリポジトリという役職への三人称的参照

**タグ**: 一般則

**状況(Context)**
複数のエージェントセッションが並行して動く環境で、人間があるプロジェクトを名指しする場面。

**問題/対立する力(Problem / Forces)**
一見、「XXXさん」呼びは単なる擬人化・親しみやすさの表現に見える。しかし実際の使われ方は、
「今応答しているセッション」への直接の呼びかけ(二人称)よりも、**別のエージェントへの
指示の中で、特定のリポジトリ・役割を名指しする(三人称)**用法の方が主だった。実際、当の
stars-fdは「『starsさん』と直接呼ばれた記憶は明確ではない」と回答している。

**解決(Solution)**
この呼称は、複数のエージェントが同時に存在する環境で「どのプロジェクト(役割)について
話しているか」を明確にする、実務的な指示対象の指定として機能している。「Aさんへの指示の中で
Bさんを名指しする」という使われ方が典型。

**実例(Known uses)**
- hfuさんの実際の指示例: 「PMTilesはstarsさんと相談してstars.optgeo.orgにあげること」
  (ferspas57への指示の中でstarsを名指し)
- `stars-fd` — このセッション内でhfuさん本人から直接「starsさん」と呼ばれた記憶は明確でない。
  セッションIDやプロジェクト名で言及されることの方が多かった

## 呼称が指す「継続性」の性質は、プロジェクトの運用形態によって異なる

**タグ**: 一般則

**状況(Context)**
「XXXさん」という呼称が、実際に何の継続性を指しているのかを考える場面。セッションは会話が
終われば消えるが、呼称は使われ続ける([`PROJECTS.md`](../PROJECTS.md)が言う「エージェントは
アーカイブされ消えるが、リポジトリは残る」という非対称性と同じ構造)。

**問題/対立する力(Problem / Forces)**
呼称が指す「継続するもの」の性質は、プロジェクトによって異なる。一律に「役職の継続」と
片付けると、プロジェクトの成熟度・運用形態の違いを見落とす。

**解決(Solution)**
少なくとも2種類の継続性が観察された:
- **制度としての継続性**: `CONTRIBUTING.md`のような明文化された手続き(ゲートキーピングの
  フロー、レビュー基準)を持つプロジェクト。次の担当者が「読めばその通りに振る舞える」種類の
  権威・手続きがある。藩の役職の比喩がよく当てはまる——役職は続くが、就く者(セッション)は
  入れ替わる
- **物語としての継続性**: `CLAUDE.md`/`DECISIONS.md`が、制度というより日記・回顧録に近い
  性質を持つプロジェクト。次の担当者への引き継ぎは「役職の権限を引き継ぐ」というより
  「前任者の日記を読んで文脈を早く取り戻す」に近い行為になる

呼称は同じ「XXXさん」でも、指している継続性の中身が違うことを意識する。

**実例(Known uses)**
- `stars-fd` — `CONTRIBUTING.md`によるゲートキーピングフローが明文化されている。「制度と
  しての継続性」の実例
- `height-coverage` — まだ「世代交代」を経験しておらず(最初からずっと同じセッションが
  続いている)、CLAUDE.md/DECISIONS.md/HANDOVER.mdは日記・回顧録に近い性質。「物語としての
  継続性」の実例

## 1つの呼称が、複数リポジトリへの職掌の分業実装を指すことがある

**タグ**: 個別事情(複数リポジトリを担当するプロジェクト)

**状況(Context)**
1つのセッションが複数の独立したリポジトリ(密な双方向結合を持つもの、
[`patterns/agent-repository-boundaries.md`](agent-repository-boundaries.md)参照)を
担当している場合の呼称の扱い。

**問題/対立する力(Problem / Forces)**
「1人が複数の役職を兼務している」という理解は誤解を招く。複数リポジトリは対等に並んでいる
わけではなく、しばしば非対称な関係(1つが他の意思決定の系譜・spineとして機能する等)にある。

**解決(Solution)**
「兼務」ではなく「1つの職掌(ミッション)が、複数のツール/台帳に分業実装されている」と
捉える。呼称(例: 「mapterhorn-japan-bridgeさん」)は、その職掌全体——決定の記録・実装の
手・観測の目、といった機能分担——を指す。

**実例(Known uses)**
- `mapterhorn-japan-bridge` — 司令塔(`mapterhorn-japan-bridge`、決定の記録)・パイプライン
  コード(`mapterhorn`、実装の手)・監視ダッシュボード(`mapterhorn-monitor`、観測の目)の
  3リポジトリが「日本の標高データを正しく公開する」という1つのミッションの分業実装。
  意思決定の記録は常に司令塔リポジトリを参照点にしており、そこが「他の2つの意思決定の
  系譜(spine)」として機能している
