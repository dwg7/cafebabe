## 中心固定型の放射状コントロール/インジケーター

**タグ**: 一般則

**状況(Context)**
MapLibre GL JSの地図上で、ある一点(クリック地点、またはサンプリング中の地点)に紐づく
複数の値やアクションを同時に提示したい場面。ポップアップやドロップダウンでは足りない
事情がある——提示したい項目が方位・順位など空間的/序列的な意味を持ち、リスト化すると
その意味が失われる。3プロジェクト(vientiane-planning-map、height-coverage、ferspas57)が
この構成に行き着いた(うち1つは移植——実例欄参照)。上記「ホバー情報は固定ドッキングパネルで
表示する」(sas0)と同じ根本問題(地点に紐づく多値情報の提示)への、別解にあたる。

**問題/対立する力(Problem / Forces)**

- **地点そのものを隠したくない**。ポップアップの箱は注目地点の上に被さる。放射状に
  「周囲へ」逃がせば中心の地点は見えたままになる
- **位置に意味を持たせたい vs 持たせなくてよい**。方位ボタンなら「ボタンの位置=見る方向」
  という直接的な空間対応が成立する(ドロップダウンの「北を見る/南を見る」でも機能はするが、
  この直接性が壊れる)。値の提示なら位置は順位の符号化に流用できる
- **タッチデバイスにはホバーが無い**。マウスカーソル追従型の設計はタッチで成立しない。
  ただしクリック(タップ)起動ならMapLibreがタップをクリックに正規化する
- **中心スロットは誤操作の名所**。開くためのクリックと中心要素のクリックが同一ジェスチャ内
  で衝突しうる(後述)
- **画面端・他UIとの干渉**。全周360°に配置すると、画面下部のパネルや地図コンテナの
  `overflow: hidden`に要素が食われることがある

**解決(Solution)**

共通機構はひとつ: アンカー点の画面座標を起点に、角度→ピクセルオフセットで各要素を配置する。
固定N方位でも、可変個の値バブルでも式は同じ。

```js
// 0°=画面上方向、時計回り。固定8方位なら angleDeg = i * 45、
// 可変 n 個を弧に並べるなら angleDeg = ARC_START + i * (ARC_END - ARC_START) / (n - 1)
function radialOffset(cx, cy, angleDeg, radius) {
  const rad = (angleDeg - 90) * Math.PI / 180;
  return { x: cx + radius * Math.cos(rad), y: cy + radius * Math.sin(rad) };
}
```

位置が「実世界の方位」を意味する場合は、画面上の角度を地図の回転に折り込んでから使う
(地図を回転させても各ボタンが正しい実方位を指す):

```js
const heading = Math.round((screenOffset + map.getBearing() + 360) % 360);
```

その上で、3実装は以下の軸で本当に分岐している。どれも各自の制約下で成立した等価な解で
あり、どれかが「完成形」なのではない。

| 軸 | vientiane-planning-map | height-coverage | ferspas57 |
|---|---|---|---|
| アンカー | クリック地点(画面上に固定) | クリック地点 | **地図の画面中心に常駐**。パンで実世界側の地点が動く |
| トリガー | クリックのみ、`map.on("click", "zoning-fill", ...)`でレイヤ限定 | クリックのみ、レイヤ制限なし(地図全域)。中央編集ボタンの出し分けのみ`buildings-not-input`ヒット判定 | イベントなし。ズーム3超で常時、`moveend`(200msデバウンス)で再サンプル |
| 中身 | アクション(Street Viewへの8方位リンク) | アクション(同8方位リンク+条件付き中央編集ボタン) | データ読み出し(地点の商品適性スコア、最大13個) |
| 符号化チャンネル | 位置=方位そのもの(罫線ではなく意味) | 同左 | 冗長多重化: 枠色(ラスタと同じ0–100ランプ)+直径(画面内min/max相対)+位置(高い順に12時から時計回り)+小さな数値表記 |
| アイコン言語 | **矢印グリフ**(↑↗→↘↓↙←↖)。方位の文字ラベル(N/NE/E...)ではなく矢印を選んだのは、地図が回転しても矢印は見た目どおりの方向を指し続けるが、文字ラベルは回転後に実際の方向と食い違うため | 未確認(ボタンの見た目については未報告) | 絵文字・旗絵文字(言語非依存。数字も言語非依存とみなし補助表示) |
| 円周 | 全周360°・固定8方位 | 全周360°・固定8方位 | 上側**約170°の弧**のみ(全周だと下位バブルが画面下部パネルに隠れた——スクリーンショットで発覚) |

個別の落とし穴と対処:

- **中央ボタンの誤発火**(vientiane-planning-mapが最初に踏んだ): 開くだけのはずのクリックで
  中央ボタンのハンドラまで同一ジェスチャ内で発火し、そのまま遷移した。ただし本人による
  明示的な留保あり——**実ブラウザ(非自動化)での再現は未確認**で、mousedown/mouseup間で
  再ヒットテストする自動化ハーネス特有の挙動かもしれない。対処は2通りが実在し、中央スロットが
  実質的な機能を持つかで分かれる:
  - **撤去**(vientiane-planning-map): 中央「方位指定なし」ボタンはGoogle側のフォールバックで
    代替可能だったため、緩和ではなく削除。副次効果としてクリック地点が隠れなくなった
  - **時間差ガード**(height-coverage): 中央の編集ボタン(iDエディタ導線)には固有の価値が
    あるため維持し、`pointer-events: none`で生成して300ms後に有効化
- **DOM配置**(vientiane-planning-map): `maplibregl.Popup`ではなく素の`<a>`を
  `position: fixed`で`document.body`直下に置く。地図コンテナ配下だと`overflow: hidden`に
  端の要素が食われる。位置は`map.getContainer().getBoundingClientRect()` + `e.point`から
  計算。閉じ条件は外側クリック(`element.contains()`)、Escape、`movestart`(パン/ズーム/回転
  で固定ピクセル位置が古くなるため)
- **絶対スケールの罠**(ferspas57): バブル直径を絶対0–100で描くと、実データが狭い帯に
  固まっていて全部同じ大きさに見えた。画面内min/max相対にして解決。半径自体も
  `clamp(60, 150, vmin*0.22)`のビューポート相対でリサイズ時に再計算

**タッチ/モバイル**: 3実装とも実機・エミュレーションでの検証は未実施。設計上の配慮には差が
ある——ferspas57はホバー非依存(パンはマウスとタッチで同一ジェスチャ)を選んでおり、他2つは
クリック起動なのでMapLibreのタップ正規化で動く「はず」——が、検証済みの実装はひとつもない。
ここは3者共通の未解決事項。

**実例(Known uses)**

3件は独立収斂ではない。系譜は次のとおり(上記「ホバー情報は固定ドッキングパネルで表示する」
とは別の、色相/彩度エントリ(`patterns/style-composition.md`)が同じ2プロジェクト間で引いた
区別と同じ流儀):

- `vientiane-planning-map`(**原型**) — 都市計画区域クリックでStreet View 8方位リンクを
  放射配置。放射レイアウト自体がユーザー指定(「関心方向は概ね一致するはずで、逆向きを
  見せられると酔う」)で、方位の空間的直接性が要件だった
- `height-coverage`(**vientiane-planning-mapからの移植、差分2点**) — 差分は
  (1) トリガーを建物限定から地図全域のクリックへ拡張(道路網も不完全なため、道路限定に
  すると同じ問題を再生産すると判断)、(2) 中央に条件付き編集ボタンを追加
  (`buildings-not-input`ヒット時のみ)し時間差ガードで維持。「円形に配置したい」という発想は
  移植元を見て採用したもので、独立に発案したものではない
- `ferspas57`(**独立設計**) — `docs/score_probe.js`。連続パン駆動サンプリング(離散
  クリックではなく)という別のインタラクションモデルで、FAO GAEZ適性スコアの多値読み出しに
  使用

## hash:"map" で名前空間化する

**タグ**: 一般則(**推奨**、hfuさん承認、2026-09-03、claude-mct実施のD6サーベイより)

**状況(Context)**
`hash: true`でURLに地図状態を保持したいが、アプリ独自の状態(パネル開閉等)もURLハッシュに
持たせたい場面。

**問題/対立する力(Problem / Forces)**
`hash: true`だと、URLハッシュがアプリ独自の状態と衝突しうる。

**解決(Solution)**
`hash: "map"`にすると、URLハッシュが`#map=z/lat/lng/bearing/pitch`と名前空間化され、
MapLibreの`Hash`クラスは自分のキー以外に手を出さなくなる。アプリ独自の状態を同じhashに
同居させられる。

**実例(Known uses)**
- `zukaku`、`height-coverage`

## UIトグルの初期状態を決め打ちせず、実際のmap状態にイベントで同期する

**タグ**: 一般則(UI)

**状況(Context)**
terrain有効/無効の切り替えチェックボックスのように、map側の状態とUI表示を一致させたい
コントロールを実装する場面。

**問題/対立する力(Problem / Forces)**
HTML側の`checked`属性とJS側のデフォルト値を二箇所で管理すると、どちらかを変更し忘れた
ときに状態がずれる。TerrainControlのような組み込みボタンからmap状態が変わった場合、
チェックボックス側だけ追従できず食い違うこともある。

**解決(Solution)**
HTML側に`checked`属性を書かず、style.json側で宣言した状態を正とする。
`map.on('terrain', () => { checkbox.checked = !!map.getTerrain(); })`のように、map自身の
状態変化イベントを購読してUIを同期させる。デフォルト値の二重管理が構造的に発生しない。

**実例(Known uses)**
- `kitavolca` — terrainチェックボックスで採用。TerrainControlボタン経由の操作でも同じ
  イベント経由でチェックボックスが追従する(2026-09-04、terrain/hillshadeヒアリングより)

## map.remove()を確実に呼ぶ(埋め込み先がビューを再構築する場合)

**タグ**: 一般則

**状況(Context)**
Open MCTのような、ビューを破棄・再構築するホスト環境にMapLibreを埋め込む場面。

**問題/対立する力(Problem / Forces)**
teardown処理が無いと、インスタンスを作り直すたびにWebGLコンテキストがリークする。

**解決(Solution)**
埋め込み先のview destroy時に`map.remove()`を確実に呼ぶ。

**実例(Known uses)**
- `sas0`(Open MCTインスツルメントとして埋め込み)

## iframe埋め込みよりネイティブ埋め込みを検討する

**問題/対立する力(Problem / Forces)**

**解決(Solution)**
ネイティブなインスツルメント/コンポーネントとして直接埋め込む形に切り替える。
