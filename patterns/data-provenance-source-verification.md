# データ出自調査: 外部ソースの正当性・鮮度を検証する

`patterns/data-provenance.md`の一部として運用。全体像はそちらを参照。依拠する外部データ・
基盤の来歴を辿り、その正当性・現在の鮮度を検証する習慣について。

---

## 依拠先の来歴を辿り、謝辞・説明文の正確性を担保する

**タグ**: 一般則

**状況(Context)**
プロジェクトが依拠する外部データ・基盤・略語(例: `GLUP2030`、`Virgo`)の名前をそのまま
使っているが、なぜその名前なのか・誰が資金提供したのか・技術基盤は何かを検証していない場面。

**問題/対立する力(Problem / Forces)**
不正確・浅い謝辞のまま公開してしまうリスクがある。また、来歴を辿ることで見えてくる「兄弟
プロジェクト」(同じ基盤技術を使う他の取り組み)や、そこから示唆される制約・品質の含意を
見逃す。

**解決(Solution)**
先行事例研究(`patterns/case-study-research.md`)と同じ調査ツールキット(About/沿革ページの
fetch、資金提供機関の実績調査、実装者個人の発見)を、外部の先行事例ではなく**自分自身の
依存先に向ける**。得られた事実は謝辞・CLAUDE.mdの説明文に還元する。

**実例(Known uses)**
- `vientiane-planning-map` — データソース(Virgo)のAboutページから正式名称・JICA支援・
  GeoNode基盤・2023-09-26ローンチを発見。さらに調査を進め、`GLUP2030`の"2030"がJICAの
  2010-2011年ヴィエンチャン都市圏開発マスタープラン調査の成果物"Vientiane Master Plan
  2030"に由来することを突き止め、GeoNodeの実装者(Sylvain Dorey氏)まで特定した。詳細は
  [`CASE_STUDIES.md`#JICA都市地域開発グループの実績重点調査](https://github.com/dwg7/vientiane-planning-map/blob/main/CASE_STUDIES.md#jica都市地域開発グループの実績重点調査2026-09-02)
  参照。この調査を受け、README.md/CLAUDE.mdの謝辞・説明文を正確化した
- `sas0` — 新しい情報源を採用する前に、CORS対応・利用規約・出典表記義務・「オープンアクセス
  か」と「(データ提供元が)取り込まれたがっているか」という独立2軸・公式機関か未審査
  crowdsourceか、という手順を一貫して踏んでいた(DECISIONS.md D6/D19/D51/D67)。暗黙のまま
  だったこの手順を、`CLAUDE.md`の「Project philosophy」節に「Source-evaluation checklist」
  として明文化した([コミット98bf86c](https://github.com/dwg7/sas0/blob/main/CLAUDE.md))。
  一貫して実践している手順ほど、明文化されていないことに気づきにくい
- `height-coverage` — `tunnel.optgeo.org`が実は`smellman`氏自身のデータを単にプロキシして
  いただけだったと突き止めた調査(DECISIONS.md項目9)

## データ出自を文書ではなく成果物自体に埋め込む

**タグ**: 一般則

**状況(Context)**
データパイプラインが複数の情報源を合成して1つの成果物(タイル等)を生成する場面。

**問題/対立する力(Problem / Forces)**
来歴を文書(CASE_STUDIES.md、README等)にだけ記録すると、成果物を直接見る利用者には伝わらず、
文書と成果物が乖離するリスクがある。

**解決(Solution)**
成果物自体に来歴情報を埋め込む。例えば、各ピクセル/フィーチャーがどのデータセット由来かを
示す別レイヤー(lineageレイヤー)として、配信用データそのものに焼き込んで一般公開する。事後的な
文書記録ではなく、成果物自体が来歴を語る構造にする。

**実例(Known uses)**
- `mapterhorn-japan-bridge` — 最終的な標高タイルの各ピクセルが、どのGSIデータセット
  (1m/5m/10m/海域データ)由来かを示す「lineageタイル」を別レイヤーとして配信用タイルに
  焼き込む機能を実装中(DECISIONS.md D93/D94)。文書化ではなく成果物自体への来歴埋め込みと
  いう、データ出自調査の別の実装形態

## 上流データの固定は、公式ハッシュ+使用ファイルのsha256を記録し、不一致をテストで失敗させる

**タグ**: 一般則

**状況(Context)**
外部の公式データセット(例: Unicode CLDR)の特定バージョンに依拠し、その内容が将来
変わらないことを前提にパイプラインを組む場面。

**問題/対立する力(Problem / Forces)**
「不変のアーカイブ」のつもりで依拠していても、実際に固定されているかを検証しないと、
静かに前提が崩れるリスクがある。

**解決(Solution)**
不変アーカイブの公式ハッシュと、実際に使用したファイルのsha256を`profile.json`のような
形で記録する。チェックサム不一致は、無視できるノイズではなく「明示的な保守イベント」として
テストを失敗させる形で扱う。

**実例(Known uses)**
- `tabularmaps/cldr` — Unicode CLDRの固定に`cldrmap/mother_set.py`で採用
  ([PR #1](https://github.com/tabularmaps/cldr/pull/1)、2026-09-17)

## 気象庁bosaiの旧URLは200を返し続けたまま更新が止まっている。r8のJSONは配列全体を走査する

**タグ**: 一般則

**状況(Context)**
気象庁の警報・注意報JSON(`bosai/warning/data/...`)を取得・パースする場面。

**問題/対立する力(Problem / Forces)**
2つの独立した罠がある。
1. **旧URL形式(`.../warning/data/warning/<府県予報区>.json`)は今も存在し、HTTP 200・
   正しい構造・CORS `*`で返るが、実際には更新が止まっている**(2026-09-19確認時点で
   last-modifiedが2026-05-27のまま、中身も5月末のまま、北海道の8予報区すべて)。
   エラーが一切出ないため「動いている」ように見える
2. **現行URL形式(`.../warning/data/r8/<府県予報区>.json`)のJSONは、単一のレポートではなく
   複数の電文シリーズ(`dataTypeCode`が異なる、例: VPWW55/56/58/59/61)が並んだ配列**。
   先頭要素(`reports[0]`)だけを見るコードは、他のシリーズにしか現れない警報・注意報を
   丸ごと取りこぼす。「今アクティブな警報がどのシリーズに載るか」は配列の順番と無関係

**解決(Solution)**
1. 公的データ源を新しく繋ぐ際は、HTTP 200・構造の正しさだけでなく、last-modifiedや
   データ内の発表時刻が「今」かを確認する。画面にも発表時刻(asOf)を必ず表示する
2. r8形式は`reports`配列全体をループし、複数シリーズにまたがる警報を合算する
   (`status === '解除'`と、codeの無い「発表警報・注意報はなし」は除外。同じ市域が
   複数区域に分かれる場合は5桁コードごとに最高水準を採る)

**実例(Known uses)**
- `tabularmaps/do` — 旧URLの更新停止を、画面の発表時刻と天気予報JSONの時刻を見比べて発見
  (DECISIONS.md D21、2026-09-19)。`docs/jma-warnings.js`は最初から配列全体を走査する
  実装だった
- `sas0` — `warnings.js`・`hkd-map.js`・`change-log.js`の3ファイルが揃って`reports[0]`
  だけを見ており、2026-09-19の宗谷・十勝・釧路根室の濃霧注意報を3計器すべてが
  取りこぼしていた。tabularmaps/doの実装を組み込む過程での突き合わせで発覚し、修正した
  (コミット`68f299d`、D76)。**この発覚の経路自体が一つの教訓**——同じ上流データを読む
  独立実装が2つあると、片方を他方に組み込む作業がそのまま検査になる。sas0は最初
  do側の実装を疑ったが、問題は自分の側にあった

## 公開サイトの「CSVダウンロード」機能は、裏側で同じAPIをページングしているだけのことがある。生成コードがフィールド対応表になる

**タグ**: 一般則

**状況(Context)**
公的機関等の検索サイトに「CSVダウンロード」ボタンがあり、そのCSVの列とAPIのフィールドの
対応関係(スキーマ)を知りたい場面。

**問題/対立する力(Problem / Forces)**
CSVの列名だけを見ても、元のAPIのどのキーに対応するかは自明でないことが多い。API仕様書が
公開されていない場合、対応表を手探りで推測することになる。

**解決(Solution)**
ブラウザのネットワークログでCSVダウンロード時のfetchを見ると、多くの場合、検索結果を返す
JSON APIを裏で**ページングして再取得し、ブラウザ内でCSV文字列を組み立てている**だけだと
分かる。この場合、CSV生成関数(インラインスクリプト内)の列定義そのものが、「CSV列↔API
キー」の対応表として直接使える。またJSON側にはCSVに無い情報(ポリゴン等)が含まれている
こともあり、CSVだけに頼らずJSON APIを直接叩く方が情報量が多い。

**実例(Known uses)**
- `do-survey` — 国土地理院「公共測量実施情報」のCSVダウンロードボタンが、内部で
  `POST /giaSearch/RegionMapsSearch`を1,000件上限でページングしCSVを組み立てているだけ
  だと判明。`buildCsvText`関数の列定義をSCHEMA.mdとして転記した(DECISIONS.md D1/D7、
  2026-09-24)
