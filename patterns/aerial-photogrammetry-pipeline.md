## ODMは同一入力・同一設定でも結果が変わる。精度は「この成果物の値」であって「この手法の値」ではない

**タグ**: 一般則

**状況(Context)**
OpenDroneMapで生成したオルソ画像・点群の精度を、成果物として公開・報告する場面。

**問題/対立する力(Problem / Forces)**
OpenSfMの逐次再構成とOpenMVSの深度マップ融合はスレッドの終了順序に依存するため、
**同一入力・同一設定(ODMバージョン・イメージID・`options.json`の差は`name`と
`project_path`のみ・境界はビット単位で同一・入力画像はハードリンク、という徹底した
同一性確認込み)で3回実行しても結果が変わる**。実測: 復元される密点群が
6.30M/7.11M/7.37M(17%の幅)、水平精度が2.09m/7.27m/9.53m、2本の成果物を共登録した際の
食い違いはパッチごとの変位の中央値28m(5m超が93%)。**同一入力で1本が2.5Dメッシュ生成中に
SIGSEGVし、別の1本は完走した**、という完走可否自体の非決定性まで確認された。

公開している成果物は、複数回実行したうちの最良(当たり)であることが多い——同じ手順を
踏んでも同じ数字は再現されない。

**解決(Solution)**
精度の書き方を変える。「**この成果物は**2.1mの精度」は正しいが、「**この手法は**2.1mの
精度」は誤り(手法の実力としては2〜10mの幅がある)。ODMを使う成果物を公開するプロジェクトは、
この区別(成果物固有の値か、手法全般の実力か)を落とさないようにする。

**実例(Known uses)**
- `tokachi20260911` — 同一入力・同一設定の3回実行で上記の非決定性を実測。境界・入力
  ファイルのビット単位での同一性を確認した上での結果(2026-09-15)

## Apple SiliconでのDocker版ODMは、NodeODMのREST APIではなくbindマウント+`run.py`直接実行で動かす

**タグ**: 一般則

**状況(Context)**
Apple Silicon Mac(colima等でDockerを動かす環境)でOpenDroneMapを実行する場面。

**問題/対立する力(Problem / Forces)**
NodeODMのREST API(`POST /task/new`)経由でタスクを投げても、colimaのポートフォワードが
大容量multipartアップロードで詰まり、何も受信されないまま応答が返らない(92MB・58枚の
アップロードで12分経ってもタスクが作られず、NodeODM側はCPU 0%・メモリ53MBのまま)。

**解決(Solution)**
バインドマウントで`run.py`を直接叩く:
```
docker run -v /path/to/work/odm:/datasets --entrypoint python3 \
  opendronemap/nodeodm /code/run.py --project-path /datasets <name> [opts]
```
`opendronemap/nodeodm`イメージにODM本体が同梱されているため、`opendronemap/odm`イメージは
別途不要。

処理前に、ODM公式が出している「枚数→必要RAM」表(500枚→32GB、1500枚→64GB目安)を確認する。
物理16GBのApple Siliconでは828枚の`--pc-quality medium`は通らず、CPU使用率17%に対し
ブロックI/O 90GBという恒常スワップに陥り2.7時間で中止に至った。`--pc-quality low`なら
同じ段階が525秒で完了する。

なお`--dem-resolution`の単位は**cm/pixel**(`2`は2cmを意味する、mではない)。

**実例(Known uses)**
- `tokachi20260911` — 上記の詰まり・スワップ・単位の3点を実機で確認(2026-09-14)

## ODMの「メモリ不足」は、出力サイズではなく点群の空間的な広がり(外れ値)が真因のことがある

**タグ**: 一般則

**状況(Context)**
OpenDroneMapが繰り返しOOM(メモリ不足)で失敗する場面。

**問題/対立する力(Problem / Forces)**
5回連続でOOMした原因は、実際にはメモリ量ではなく**密点群の空間的な広がり**だった——
12km²の調査対象に対し、密点群がX方向3,525kmにまで広がっており、ODMがこれをグリッド化
しようとして破綻していた。`--pc-filter`(既定2.5σ)は**局所フィルタ**であり、孤立した
遠方の外れ値(近傍点が少ないため統計的に弾かれない)を除去できない。この状態では
**split-mergeも救済にならない**——250枚/overlap 150で分割しても、原因が点群の空間的な
広がりである以上、各サブモデルが同じ外れ値を抱えたままオルソ生成でOOMする。

**解決(Solution)**
「メモリ不足」というエラーが出たら、出力(結果の点群)ではなく**入力(カメラ位置)の空間的
範囲を測る**。`--boundary`にカメラ位置の凸包+バッファを渡すことで、点群の範囲を強制的に
限定できる。実例では中間ファイルが195GB→11MBまで縮小し、処理が完走した。`--boundary`で
解決した後は、split-mergeによる分割自体が不要になった。

**実例(Known uses)**
- `tokachi20260911` — 5回のOOM失敗の後、`--boundary`指定で解決(2026-09-14)

## PMTiles生成・配信の落とし穴: メタデータは生成時に埋める、`name`をソースIDと一致させない、bounds/centerは明示する

**タグ**: 一般則

**状況(Context)**
オルソ画像等のラスタをPMTiles化し、Martin等のタイルサーバーで配信する場面
(`gdalwarp`→MBTiles(WebP)→`gdaladdo`→`pmtiles convert`という経路)。

**問題/対立する力(Problem / Forces)**
3つの落とし穴を実際に踏んだ:
- メタデータは配信側で上書きできない。生成時に埋め損ねると、後から直すのにファイル全体の
  書き直しが必要になる
- PMTilesの`name`フィールドをソースID(Martinのカタログ上のID)と一致させると、**Martin側の
  フィルタ処理(`.filter(|v| *v != id)`)により、カタログから消える**
- `bounds`/`center`をGDAL任せにすると、`bounds`自体は正しいのに`center`の経度だけ
  -72のように壊れることがある

**解決(Solution)**
生成時にメタデータを確定させる。`name`をソースIDと同一にしない。`bounds`/`center`は
明示的に指定する。

**実例(Known uses)**
- `tokachi20260911` — 上記3点を実機のMartin配信(stars)で確認(2026-09-14)

## stars(Martin + Cloudflare)はメタデータを4時間キャッシュする。差し替え直後の検証にはキャッシュバスタが必須

**タグ**: 個別事情(stars)

**状況(Context)**
`stars.optgeo.org`(Martin配信、Cloudflareが前段)へPMTilesを差し替えた直後に、反映を
確認する場面。

**問題/対立する力(Problem / Forces)**
starsのメタデータ応答は`max-age=14400`(4時間)でキャッシュされる。差し替え直後に素の
`curl`で確認すると古い内容が返ってきて、「反映されていない」と誤判定しかける。

**解決(Solution)**
確認時はクエリ文字列を足すなどしてキャッシュを明示的に外してから検証する。

**実例(Known uses)**
- `tokachi20260911` — オルソ画像PMTilesの差し替え直後、キャッシュされた古いメタデータを
  見て誤判定しかけた(2026-09-14)

**訂正(2026-09-14、stars本人の返信より)**: この2点(`name`=ID衝突・4時間キャッシュ)は
実はstars側が先に踏んで`docs/KNOWN_FACTS.md`(starsはDECISIONS.mdではなくこちらを一次
情報源にしている)に記録済みの既知の事実だった。stars自身は2026-09-07(`kitaphoto`)・
2026-09-11(`mapterhorn-japan-bridge-lineage`)で`name`=ID衝突を踏んでおり、事前に
tokachi20260911へ伝えていたため、tokachi20260911は最初からIDと別の表示名を使っていた
(=このKnown usesの書き方は不正確で、「tokachi20260911が発見した」のではなく
「starsから事前に伝えられていた知見を、tokachi20260911がcafebabeへ再共有した」が正確)。

stars本人の分類整理: `name`=ID衝突は**Martinを使う配信者全般に効く一般則**、
4時間キャッシュは**Cloudflareを前段に置く構成一般に効く**——「個別事情(stars)」タグは
実例が今のところstars 1件のみである以上妥当だが、当てはまる範囲はより広い可能性が高い。

**追加知見(stars、GitHub Pages側の類似の罠)**: `fetch(..., {cache: "no-store"})`は
ブラウザキャッシュしか回避せず、GitHub Pages前段のCDNは素通りしない。このため、
デプロイ直後は(ブラウザ側は最新を要求しているにも関わらず)CDNにキャッシュされた古い
404がしばらく返り続けることがある。starsの監視ダッシュボード運用で記録済み。

**実例(Known uses、追加)**:
- `stars` — Martin(`martin-core/src/tiles/source.rs`の
  `tilejson.name.as_ref().filter(|v| *v != id)`)による`name`=ID衝突を2026-09-07・
  2026-09-11の2回実地で確認。GitHub Pages CDNが`no-store`を素通りしデプロイ直後に
  古い404を返し続ける件も確認済み

## 二時期のオルソ画像が共登録できるかは、位相相関の弱ピーク棄却率で事前に見積もれる

**タグ**: 一般則

**状況(Context)**
自前で生成したオルソ画像を、既存の空中写真(別時期撮影)と位置合わせ(共登録)できるか
どうかを、本番の位置合わせ処理を回す前に見積もりたい場面。

**問題/対立する力(Problem / Forces)**
共登録の成否は、対象の地面が二時期の間で変化していないかに強く依存する——裸地・岩・
涸れ沢は年を跨いでも模様が同じだが、森林の樹冠は季節・年で変わり、河原は出水で動き、
農地は輪作で中身が入れ替わる。この「地面の時間的安定性」を、実際に位置合わせを回すまで
確認する手段が無いと、失敗してから気づくことになる。

**解決(Solution)**
位相相関(phase correlation)の弱ピーク棄却率を、共登録可能性の事前指標として使う
(実例: 火口52% / 市街地70% / 農地71% / 森林・河畔91%——値が高いほど共登録しにくい)。
ただし**棄却率は被写体だけの性質ではなく、「被写体の時間的安定性」と「自分のオルソ自体の
歪み」の積**であることに注意する——自分のオルソが歪んでいれば、被写体側の条件が良くても
高い棄却率になりうる。

**実例(Known uses)**
- `tokachi20260911` — 標高帯別(森林・渓谷/裸地の火山斜面/山頂・噴煙域)の位置合わせ成功率が
  16%/61%/28%と非単調に変化する現象を、位相相関棄却率(91%/52%台)で説明できた
  (2026-09-14)。当初仮説だった「噴煙シグネチャ(明るさ・彩度・局所テクスチャ)による
  層別」は明るさ・彩度・局所テクスチャのいずれとも相関せず(採用率22〜43%、単調性なし)、
  支持されなかった——土地被覆(地面の時間的安定性)の方が効いていた
