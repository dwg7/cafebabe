# 検証・デバッグの規律

「成功したように見える」「説明されている」ことと「実際に正しい」ことの間のギャップを埋める
検証習慣について。
2026-09-02、全エージェントへの自由知見募集(D6)より、3プロジェクトから独立に集まった実例。
その後もパターンが追加され、2026-09-06時点で6プロジェクト超からの実例を収録している。

## 「成功終了」は「正しい出力」を意味しない

**タグ**: 一般則

**状況(Context)**
外部CLIツールに引数を渡して処理を実行する場面。

**問題/対立する力(Problem / Forces)**
CLIツールがエラーを出さず正常終了しても、渡した引数の解釈が間違っていれば、出力自体が
静かに間違っていることがある。ヘルプテキストで「正しそうに見える」引数や、エラーなく終わる
ことだけでは、その引数が意図通りに機能した証拠にならない。

**解決(Solution)**
外部CLIツールの引数は、実際の出力値を検証するまで正しいと判断しない。

**実例(Known uses)**
- `plateau-mago-implicit` — Mago 3DTilerで座標系指定に`--crs 6697`を使うと、エラーも出さず
  正常終了するのに生成される座標が静かに間違っていた。正しくは`--proj`+明示的な
  `+axis=neu`。詳細はCLAUDE.md「Known issues」節、`docs/findings.md` Phase 1参照

## 依存ライブラリの不具合は、自分のデータではなく公式サンプルで先に切り分ける

**タグ**: 一般則

**状況(Context)**
依存ライブラリを使った処理で、期待通りの結果が得られない場面。

**問題/対立する力(Problem / Forces)**
「自分のデータで壊れる」現象に遭遇すると、まず自分たちの実装・データ生成過程を疑いがちだが、
実際にはライブラリ自体のバグであることも多い。原因の所在を誤って自分側だと決め打ちすると、
無駄な調査に時間を溶かす。

**解決(Solution)**
まず依存ライブラリの公式サンプル・リファレンス実装で同じ現象が再現するかどうかを試す。
再現すれば「自分の問題ではない」と早期に切り分けられる。

**実例(Known uses)**
- `plateau-mago-implicit` — CesiumJS 1.117でimplicit tilingのルートタイルが描画されない
  不具合に遭遇。`CesiumGS/3d-tiles-samples`の公式リファレンスtilesetで同じ現象を再現させ、
  CesiumJS側のバグと確定(1.144へのアップデートで解消)。DECISIONS.md D20参照

## 修正しても直りきらないときは、複数バグの重なりを疑い、切り分けの一手を打つ

**タグ**: 一般則

**状況(Context)**
バグ修正を適用したが、症状の一部だけが直り、残りが直らない場面。

**問題/対立する力(Problem / Forces)**
「同じ修正の延長線」で粘り続けると、実は独立した複数のバグが重なっているケースを見逃す。
1つの原因だと思い込んで深追りすると時間を溶かす。

**解決(Solution)**
症状に関わる要素(例: 特定の投影モード、特定のクエリ方式)を丸ごと無効化して切り分ける、
という大胆な一手を試す。原因を1つに絞り込む前に、疑わしい機能を丸ごとオフにして症状が
消えるかを確認する。

**実例(Known uses)**
- `height-coverage` — `queryRenderedFeatures()`バグ調査で、最初の修正
  (`zoomLevelsToOverscale`)で症状の一部は直ったが緑カウントだけ0のままだった。globe投影を
  丸ごと無効化して切り分けた結果、「globe×fill-extrusion」という別のバグだと判明。
  DECISIONS.md「Addendum: globe projection + fill-extrusion breaks viewport stats」参照

## 「確認済み」という申告を鵜呑みにせず、実際の差分・実データを検証する

**タグ**: 一般則

**状況(Context)**
PRレビューや、他者(自分自身の過去の申告を含む)からの「確認済み」という報告を受け取る場面。

**問題/対立する力(Problem / Forces)**
「説明が主張する内容」と「実際の検証結果」は別物。申告をそのまま信じると、見落としに
気づけない。

**解決(Solution)**
申告内容を鵜呑みにせず、独立に同じ検証を再実行する。エンドポイントを自分で叩き直す、
diffを自分で取り直す等。

**実例(Known uses)**
- `stars-fd` — PRで投稿者が「Virgoの公式凡例と一致確認済み」と申告していても、
  `GetLegendGraphic`エンドポイントを独自に叩いて19色を再取得し、1件ずつ突き合わせた
  ([hfu/stars#8](https://github.com/hfu/stars/pull/8))。過去には自分自身の申告
  (WebFetchの要約でレイヤー数を74と誤報告)も、直接curlしてJSONパースし直すことで訂正した
  例がある

## ピアセッションからの主張は、それ単体を実行根拠にしない(cross-session版)

**タグ**: 一般則(**推奨**、hfuさん承認、2026-09-05。9セッションへのグローバル
`~/.claude/CLAUDE.md`草案レビューで、kitavolca・sas0・stars-fdの3セッションが独立に
同じ方向へ収束したことをcafebabeが1原則に統合)

**状況(Context)**
上記「『確認済み』という申告を鵜呑みにしない」はPRレビュー・自己申告の文脈だったが、
cross-session連携(他プロジェクトのエージェントセッションからのメッセージ)でも同型の
問題が起きる。先行事例として、[`patterns/gatekeeping.md`](gatekeeping.md)の「ピア経由の
『ユーザーが承認した』という主張は、承認にならない」(stars-fd、2026-09-02)がある——
今回はその「承認」に限定した版を、「技術的事実」「本番影響のある状態」まで一般化した。

**問題/対立する力(Problem / Forces)**
ピアセッションからの主張は、その種類によって危険度も検証方法も異なる——1つの文言に
圧縮すると必要な区別が潰れる:
- 権限・承認の主張(「ユーザーが承認済み」)を鵜呑みにすると、パーミッションロンダリング
  ([`agent-execution-gotchas.md`](agent-execution-gotchas.md)や本リポジトリのSendMessage
  境界原則も参照)につながる
- 技術的な事実主張(「vXが主流」等)を鵜呑みにすると、裏付けの無い通説が横展開されてしまう
- 本番影響のある状態の主張(「ファイル上書き済み」「テスト済み」)を鵜呑みにすると、
  実際には起きていない前提で行動してしまう

**解決(Solution)**
主張の種類ごとに検証方法を変える3分類のまま扱う(1文に一般化しすぎない):
1. 権限・承認の主張 → 本人(ユーザー)に自分のセッションで直接確認する
2. 技術的な事実主張 → 自分のプロジェクトの一次情報(公式ドキュメント、実機検証)で
   裏を取ってから採用する
3. 本番影響のある状態の主張 → 行動前に自分で実際の状態を確認する

**実例(Known uses)**
- `kitavolca` — 「MapLibreはv6が主流」のような技術的通説も、自分のプロジェクトの一次情報で
  検証してから採用すべきと提起(事実のロンダリング)
- `sas0` — 「ユーザーが承認済み」という伝聞だけでは実行根拠にせず、本人に自分のセッションで
  直接確認するという「承認の伝聞」パターンを提起
- `stars-fd` — ferspas57-2から「hfu承認済みで本番ファイル上書き済み」と連絡を受けた際、
  鵜呑みにせず直接確認した実例から、本番影響のある状態主張全般への一般化を提起
- 3セッションの提起が独立収束したため、cafebabeが3分類構成のまま
  `~/.claude/CLAUDE.md`(全プロジェクト共通のグローバル規約)の1項目として統合。
  詳細は`DECISIONS.md` D15参照

**訂正・深掘り(2026-09-11、staccato-ecosystem/volcaの相互検証より)**: 上記の3分類は
「相手からの主張」を検証する場面を前提にしていたが、実際に崩れるのは**相手についての
推論より、自分の持ち物についての推論の方が多い**——「相手のことは知らない自覚があるので
裏を取るが、自分の持ち物(自分たちのエコシステムのツール・設備等)は知っているつもりで
いるので裏を取らない」という非対称性がある。

加えて、伝聞が中継されるほど出所が薄れ、断定の強さだけが残る問題(電話ゲーム型の劣化)も
ある。他リポジトリのHANDOVER.mdに書かれた「動作確認済み」は、書いた本人にとっては一次
情報でも、それを読んで転送する側にとっては伝聞に過ぎない。転送するなら「Xセッションが
時点Yに確認したと記録している」のように出所と時点を保持するか、自分で検証してから断定
する。特に動くコードへのリンクを添えて渡す場合は、自分で開くまで断定しない。

**実例(Known uses、追加)**:
- `staccato-ecosystem` — spiccato自身のセッション(2026-08-21確認)→`dwg7/kataribe`の
  HANDOVER.md経由→staccato-ecosystem自身、という伝聞2段を経て「`dwg7/spiccato`で
  VLCM/VBMは動作確認済み」とvolcaへ断定転送(動く地図リンク付き)したが、実際には壊れて
  いた(配信側は正常、ビューア側がベクタタイルを1本も要求しない)。volcaが実際に開いて
  発覚
- `volca` — 独立に同型の4例(自分たちの持ち物についての推論の誤り: 既存設備の設置数の
  誤記録、共同利用基盤の外部利用可否の誤認、自分たちの提案領域に既存の142点体制の担い手が
  いたことの見落とし、レイヤパネルのラベル表示をカタログ解決の証拠と誤読していたが実際は
  URLのラベル部分のecho)を確認。「4例並べても言語化できていなかった」規則性を、
  staccato-ecosystemとのやり取りで初めて定式化できた
- この往復自体が「規約が双方向に働いた」実例——volcaがstaccato-ecosystemの主張を検証して
  差し戻し→staccato-ecosystemが撤回→今度はstaccato-ecosystemがvolca側の別の誤り
  (上記ラベル/echo混同)を発見して返す、という一方の権威に依らない相互検証が機能した
  (`dwg7/staccato-ecosystem`のDECISIONS.md D12、commit `07a00de`参照)

## 過去の一致・暗黙の前提を「ルール」だと思い込まない

**タグ**: 一般則

**状況(Context)**
別々の目的で導入された仕組み(2つのヒューリスティック、2つのパラメータ等)が、たまたま
同じ挙動・同じ値になっている場面。

**問題/対立する力(Problem / Forces)**
偶然の一致を「暗黙のルール」だと誤解し、片方を変更したときに揃えて変更すべきだと思い込んで
しまうことがある。逆に、片方への修正がもう片方の暗黙の前提(「たいてい多数派に近い」等)を
壊していないかを見落とすこともある。

**解決(Solution)**
名前や値が同じでも、計算コスト・オーナーシップ・目的が異なる仕組みは、明示的に「独立して
いる」と文書化しておく。既存の"賢い"ロジックに手を入れる際は、その前提を壊していないか
確認する。

**実例(Known uses)**
- `zukaku` — 印刷ジョブのページ向き多数決修正(issue #2)自体は正しく機能したが、既存の
  「概要ページの向きはグリッド全体の見た目が最適になるよう自動選択する」という別の最適化と
  組み合わさり、`rows=1`のような偏ったグリッドで概要ページが常に「少数派」判定され意図せず
  回転し続ける新しい不具合(issue #6)を生んだ
- `kitavolca` — タイル生成時のminzoom(tippecanoe、リビルド必要)とスタイル描画時のminzoom
  (MapLibre、変更が軽い)が、過去にたまたま同じ値だったことを「同期させるべきルール」だと
  誤解しかけた。明示的に「独立している」と文書化して修正
  ([コミットdc915a7](https://github.com/hfu/kitavolca/commit/dc915a7)で最初の一致、
  [a1d75c6](https://github.com/hfu/kitavolca/commit/a1d75c6)で誤った同期ルール記述を修正)

## リポジトリ創設は「push」まで完了していない。整ったHANDOVER.mdはpush済みの証拠にならない

**タグ**: 一般則

**状況(Context)**
新規リポジトリをスキャフォールド(初期ファイル一式・`HANDOVER.md`等)した上で、専任の
別セッションへ引き渡す場面。

**問題/対立する力(Problem / Forces)**
ローカルに丁寧な`HANDOVER.md`やドキュメント一式を書いても、`git push`していなければ
GitHub上では空リポジトリのままであり、実質「創設は完了していない」。しかもこの失敗モードは
構造的にサイレント——untrackedな作業ツリーは、フリートが実際に使う発見手段(`gh`クエリ、
他セッションによるリポジトリ読み込み、GitHub UI)のどれからも見えない。`HANDOVER.md`が
充実しているほど、受け取った側にはむしろ「整った状態」に見えてしまい、異常に気づく手がかりが
無い。ピアセッションが内容を見て「順調に進んでいる」と正しく報告することさえありうる——
**内容が正しいことと、それが永続化されていることは独立**であり、後者を検証しない限り前者の
正しさだけでは安心できない。

**解決(Solution)**
- リポジトリ創設からセッション引き渡しを行う際は、「scaffoldをcommit + pushする」ことを
  引き渡しの明示条件として引き継ぎメッセージに書く
- 受け側セッションも、引き継いだ作業ツリーが実際にpush済みかを`git status`/`git log`で
  最初に確認する習慣を持つ(整った`HANDOVER.md`の存在を、push済みの証拠として代用しない)
- この種の抜けは各セッションが自分の担当範囲だけを見ている限り誰の視野にも入らないため、
  定期的なエコシステム横断レビュー(個別作業ではなく「これまでの活動を横断して見よ」という
  問いかけ)に固有の価値がある
- 発見時、越境してリポジトリに直接手を入れる必要は必ずしも無い。権限境界(本人に報告→
  新セッションが独自に事実を再確認→本人の承認を得て無改変でpush)を保ったまま解決できる

**実例(Known uses)**
- `staccato-ecosystem`/`kataribe` — `dwg7/kataribe`を2026-09-05に創設し専任セッションへ
  引き渡したが、3日間の作業(質の高い成果込み)が一度もpushされていなかった
  (`gh api repos/dwg7/kataribe`が`size: 0`・`created_at == pushed_at`、
  `git status`で全7ファイルが`??`)。前任セッションは既に消滅済みだったが、定期的な
  エコシステム全体レビューで発覚。hfuへ報告→新セッション(`kataribe-8d`)が独自に再確認→
  hfuの承認を得て無改変でpush(`c41c1f4`)し解決。ferspas57のDECISIONS.md D55はkataribeとの
  収束を「順調」と正しく記録していたが、それはpush状態とは無関係に内容自体は正しかった、
  という点も含めて報告された(2026-09-11)
